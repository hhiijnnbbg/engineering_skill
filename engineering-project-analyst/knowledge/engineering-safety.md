# 工业软件安全规则

本 Skill 区别于普通 AI 的核心约束。所有 change-plan 必须逐条核对。

## 禁止修改层

以下层次默认禁止修改，除非用户明确要求：

```text
Camera SDK Layer     — 相机 SDK 封装层
Hardware Driver      — 硬件驱动相关
Database Core        — 数据库核心访问层
```

原因：这些层经过长期现场验证，修改风险远高于收益。确需变更时，优先在上层做适配。

## 修改评审例外机制

禁止修改层为默认保护，并非绝对不可触碰。当出现以下情形时，允许进入修改评审流程：

```text
触发条件（需同时满足）:
1. 用户明确授权修改该层
2. 上层适配方案已被证明不可行
3. 已给出影响分析（波及范围 / 兼容性）
4. 已给出回滚方案
```

评审流程：

1. 先在上层尝试适配，记录失败原因
2. 输出影响分析与回滚方案，交用户确认
3. 用户授权后，方可进入 change-plan 并标注"例外修改"
4. 修改范围尽量最小化，保持接口对外稳定

未经此流程，Agent 不得自行提议或执行对禁止修改层的改动。

## 稳定性要求

任何方案必须回答以下问题：

### 掉线

- 设备掉线时系统行为是什么？
- 重连后状态如何恢复？
- 掉线期间的数据是否丢失，丢失是否可接受？

### 异常恢复

- 进程异常退出后，未保存的数据怎么办？
- 文件（视频/记录）是否可能损坏，如何缩小损坏窗口？
- 重启后能否回到一致的状态？

### 资源释放

- 异常路径上资源是否仍会释放？（try-finally / Dispose）
- 长时间运行是否存在缓慢泄漏？（句柄、内存、文件句柄）

### 数据一致性

- 写入是否是原子的或有失败回滚？
- 多线程/异步下共享状态是否有保护？

## 方案红线

出现以下情况的方案直接否决或要求重做：

- 在 UI 线程执行 SDK 阻塞调用
- 修改禁止修改层且未走修改评审例外机制
- 无异常恢复设计的长时运行任务
- 破坏现有状态机合法跳转路径
